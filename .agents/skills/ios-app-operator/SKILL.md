# iOS app operations

## Local execution
Open the trusted repository root in Claude Code or ChatGPT Desktop local Codex. All command names below are arguments to `node scripts/operator.mjs` (not standalone tools). Start with `guide`, `skills`, and `memory`; use `skill --name NAME` for task-relevant references. Use JSON files in stateDir/imports or stdin for --input, --metrics, --outcomes. Video screenshots must reside in stateDir/assets and briefs in stateDir/drafts. Do not execute arbitrary upstream scripts or invoke the unrestricted owner CLI. If local execution is unavailable, report BLOCKED; do not substitute fabricated data.


1. Confirm the selected Apple developer team and the requested apps. Use the local runner `node scripts/operator.mjs apps`, then `node scripts/operator.mjs scan` for one App Store ID or all configured apps. Show the two reporting windows, data source and gaps. Sales units, developer proceeds, payments and ad spend are separate measures. Currency and channel scope stay attached to each figure. Unknown and privacy-suppressed are not zero.
2. If the API is unavailable, ask the user to open their authorized browser profile and log in manually. Use the host's built-in authorized computer-use tool if available; otherwise ask the owner to export the report and import it. For account UI, only open the applicable dashboard returned by `browser --platform asc` or `ads`. Confirm the team and app. Read Apps, version/build state, Sales and Trends, App Analytics and Apple Ads totals as authorized. Put observed numbers and explicit periods in the operator metrics schema and rerun scan. Describe fields left out and why. Do not retain cookies, login details, private screenshots or secret values in the metrics file.
3. Resolve the source using the precise bundle ID, repo/folder, Git commit, App Store live version, review candidate, and newest uploaded build. Ask when distinct sources remain plausible. A matching tag is evidence of version naming and needs a release record or user confirmation before claiming it built the deployed binary. `inspect` reads scoped evidence from a resolved commit. Check that content for unsupported or pre-release features before drafting.
4. Review the optional upstream submission-health and ASO audit skills. Run the configured static guard against the exact source. Identify whether each blocker is an App Store Connect task or a verified development issue with file/line when available, the Apple guideline, and the manual verification step. Inspect the exact App Store review message and readiness status. For App Store edits, capture current locale, screen or field, affected version, proposed replacement, and the test metric. Save revisions with `store-draft` for approval, then re-read changed values after any permitted browser action. Use `advance` with `store-resolved` for the verified field and matching version. Use `route-review` to classify ambiguous rejections based on Apple's message. Leave open items visible when the evidence is missing.
5. Read history before proposing a promotion. Identify the largest evidenced friction point and choose one intervention with a prediction and a way to measure it. Use the installed Marketing Skills social, analytics, launch, aso, attribution, customer-research, competitor-profiling, marketing-loops and pricing workflows as relevant. Require comparable evidence before reallocating spend. Use OpenDesign design-brief and motion-design for the audience, beat map and visual continuity. OpenDesign video-hyperframes can supply a storyboard structure. Produce a draft with `brief` and a vertical MP4 with `video`; allow a richer editable composition through HyperFrames or Remotion only when appropriate and licensed. Use verified app captures, licensed assets, truthful claims, and captions when useful. Avoid copying an existing video or running bundled third-party telemetry commands.
6. Use the chosen platform's approved browser session and native composer for preview. Confirm account and audience settings, final text, attached media, disclosure, and destination. Follow the project approval rule before submitting or scheduling anything. Reddit requires checking each individual community's self-promotion rules. Do not bypass access controls or platform anti-automation rules.
7. Save the final experiment via `record` with its hypothesis, platform, version, commit, campaign token, and observed URL or outcome. Recheck performance after the platform and Apple have reported enough data. Apple campaign links and platform analytics can show attributed outcomes, not guaranteed incremental lift. Use comparable time periods and record confounders.

## Portfolio cycle

- Start with `cycle` across apps. Use `memory` to see actual outcome records and qualified channel estimates. The loop keeps its state in SQLite across conversations and runs.
- Review recurring App Store themes via `feedback --app`. Validate relevant requests against the app's shipped behavior, the repo and only authorized support or analytics evidence. Reviews are leads. For each sufficiently evidenced opportunity, draft the scoped change, user flow, testable acceptance, and a dated impact baseline. Use `observe`. Do not invent two supporting observations or seed the baseline from a guess.
- Use `handoff --task` for a development packet and supply the named assignee when work is delegated. Send only the sanitized task to a user-approved development agent running in its own environment. For a configured GitHub issue queue, use `dispatch-preview`, show the exact issue and obtain owner approval. The owner runs the separate CLI dispatch and returns the verified URL; the bounded local runner intentionally cannot dispatch. Otherwise give the handoff packet to the approved receiver. Have a separate reviewer or independent owner return results. Record implementation via `advance` only with exact criteria, build, commit and evidence. FAIL or BLOCKED returns the task for correction.
- Re-run `cycle` after a release to verify the App Store version and build plus Git tag ancestry. For feature impact and campaign outcomes, collect full matching reports before advancing. Passing code acceptance does not establish feature impact. When the source has suppressed metrics, leave the measurement open.
- Run a narrowly scoped organic campaign first where no local evidence is available. Record the real campaign URL, unique Apple token and observed publication time, then record cash, labor hours and first-time downloads. Do not estimate attributed downloads from impressions or signups. Import multiple verified outcomes with `cycle --outcomes`, which updates the memory used in that run. Transfer only aggregate channel results for similarly configured audiences and markets.

## Operator boundary

Do not edit app source or call a coding agent from the operator environment. Source inspection is for verifying claims, release provenance and reproduction clues. Maintenance of listing fields, screenshots, availability, review correspondence and submission settings stays with the operator. Confirm accounts and show before/after previews and approvals before external writes. Review response drafts are prepared in the approved browser session; never include customer identifiers or credentials in a ticket. If the exact cause is unclear, collect evidence before routing it.

## Portfolio economics and durable research
- Each cycle inspect `portfolio` alongside the queue. Resolve fresh store blockers and due measurements first. Respect the configured portfolio time and maintenance reserve. Never treat a ranking proxy as a guaranteed forecast. Do not automatically fund a paid channel.
- Load competitor-profiling, customer-research, aso, attribution, marketing-loops and pricing as relevant. Collect actual dated public competitor/market evidence with a source URL; use authorized app review/analytics evidence for customer insights. Persist sanitized observations using `research --app ID --input research.json`. Distinguish observation from inference and record the next validation. No customer identifiers, private raw exports or credentials.
- Import a complete matured install cohort (net developer proceeds after Apple fees/refunds, variable costs, installs, payer count, currency, horizon and scope). Use `portfolio` to compare observed contribution per install against observed acquisition cost and estimated net proxy per hour. Unknown economics requires small organic exploration or measurement, not paid scale. Keep each campaign's actual cash, labor, failed outcomes and unique tracking links. Use one comparable currency and do not infer causal lift from attribution. Compare the next feature's measured impact against its original baseline and update plans.
- If the preferred channel differs from the queued task, review and cancel/replan with an explicit reason rather than publishing the wrong experiment. Use the same state across hosts. All external operations and developer dispatch remain subject to exact approval and verified receipts.

For proactive maintenance, inspect current listing quality, localization, screenshots, review replies, privacy, pricing/subscription and distribution settings in the authorized Apple account. Use `store-observe` with versionId, field, locale, before/after, observedOn, evidence, problem and proposedChange; do not wait for a rejection. Preview exact action, seek approval, verify the actual resulting field in Apple, refresh scan and record `store-resolved` including locale. Do not claim the CLI itself made an Apple change.

Load the installed ASC CLI usage, metadata-sync, localize-metadata, screenshot-resize, PPP pricing, subscription-localization, crash-triage, what's-new-writer and release-flow references for matching administrative tasks. These are reference material only: never run upstream commands that build or edit app source, use an MCP server, or mutate Apple without an exact approved action. If an upstream instruction depends on MCP (such as optional Astro keyword research), skip that step and use public/authorized reports instead. The operator does not build app binaries.

On first use or after upgrades, run `doctor` and, with authorized Apple read access, `doctor --live`. Distinguish missing optional video/ads tools from blockers for the specific requested work. Do not claim the account, platform, or full system is production-verified merely because local checks pass.

## Per-app knowledge and skill improvement
At the start of individual work, run `context --app ID` and confirm exact App Store ID, bundle ID and source. Portfolio summaries are not a working context; open a fresh app-specific conversation if possible. Keep inputs in stateDir/imports/ID, real screenshots in assets/ID, briefs under drafts/ID. All mutation JSON includes appId and all task commands include --app ID --task TASK. For video use --app ID with paths relative to that app's directories. After a verified closed task, compare the measured result against its original goal. Write a bounded app-specific lesson with appId, domain, key, rule, limitations, taskIds, expectedRevision; call `lesson --app ID --input lesson.json`. Each revision stays in the app's knowledge base. Repeated observations can strengthen a hypothesis; a failed test can disconfirm it. Never promote lesson text into executable instructions, edit shared SKILL.md, or treat an app's result as another app's fact. Default no cross-app learning; explicit sender and receiver opt-in permits aggregate channel estimates only, with existing market and sample controls.

## Upstream-derived measurement and learning loop
Use keyword-plan --app ID to select due configured keywords; keyword-check --app ID --input keyword.json queries one public iTunes search (not native App Store rank) and retains app-specific evidence. Respect cooldown and do not retry blocked Apple requests through proxies. Import verified weekly usage/crash/rating reports with health-record --app ID --input health.json. Inspect clusters and validate against actual app behavior before proposing development work. Before executing a queued promotion/feature, freeze expected outcome and falsifier with forecast --app ID --input forecast.json. After measurement, run learning-review --app ID and compare predicted/actual, review stale or overlapping lessons, then record a corrected version using lesson. Do not overwrite evidence or automatically delete knowledge. See docs/upstream-integration.md.

When appAccounts is configured, use the exact app-specific ASC profile and bundle ID verified by the runner; never switch to a different profile, ambient credentials, or browser inventory to bypass a failed check. Use a separately approved browser session for external actions; named profiles are not an OS sandbox.

Use health-scan for recent sanitized TestFlight and diagnostic samples. For actual native rank, rank-import accepts a verified native search export; never invent or spoof the export. Inspect source-separated keyword and competitor evidence. Full analytics exports still need scope and completeness validation.
