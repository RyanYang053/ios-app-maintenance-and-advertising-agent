# iOS app operations

## Local execution
Open the trusted repository root in Claude Code or ChatGPT Desktop local Codex. All command names below are arguments to `node scripts/operator.mjs` (not standalone tools). Start with `guide`, `skills`, and `memory`; use `skill --name NAME` for task-relevant references. Then run `status`: it lists every app with what is done, what is blocked and the exact next command; work from it instead of guessing. Before writing any JSON input, run `schema --name ACTION` (for advance use `schema --name advance` then e.g. `advance:post`) and copy its field list; never guess fields. When a command fails, the runner returns the exact validation message: fix that field and retry once, do not loop blindly. Use JSON files in stateDir/imports or stdin for --input, --metrics, --outcomes. Video screenshots must reside in stateDir/assets and briefs in stateDir/drafts. Do not execute arbitrary upstream scripts or invoke the unrestricted owner CLI. If local execution is unavailable, report BLOCKED; do not substitute fabricated data.


1. Confirm the selected Apple developer team and the requested apps. Use the local runner `node scripts/operator.mjs apps`, then `node scripts/operator.mjs scan` for one App Store ID or all configured apps. Show the two reporting windows, data source and gaps. Sales units, developer proceeds, payments and ad spend are separate measures. Currency and channel scope stay attached to each figure. Unknown and privacy-suppressed are not zero.
2. If the API is unavailable, ask the user to open their authorized browser profile and log in manually. Use the host's built-in authorized computer-use tool if available; otherwise ask the owner to export the report and import it. For account UI, only open the applicable dashboard returned by `browser --platform asc` or `ads`. Confirm the team and app. Read Apps, version/build state, Sales and Trends, App Analytics and Apple Ads totals as authorized. Put observed numbers and explicit periods in the operator metrics schema and rerun scan. Describe fields left out and why. Do not retain cookies, login details, private screenshots or secret values in the metrics file.
3. Find the source. First read the ledger: `context --app ID` and `history --app ID` show the source this app was matched to before; reuse it. If there is none, run `discover-sources`: it matches each app's bundle ID to local Xcode projects under the owner's `sourceDiscovery.roots` and lists every copy (remote, latest commit, live-version tags). Never search outside those roots, and never read other agents' transcripts or home dotfolders to find code. When several copies exist (for example one per coding agent), show them to the owner and record the shipping copy with `source-confirm`; then `scan --app ID`. Read code only through `inspect --app ID --release` (index), `--file PATH` (one file, secrets redacted) and `--query TEXT` (search); cite file:line in claims. Resolve the source using the precise bundle ID, repo/folder, Git commit, App Store live version, review candidate, and newest uploaded build. Ask when distinct sources remain plausible. A matching tag is evidence of version naming and needs a release record or user confirmation before claiming it built the deployed binary. `inspect` reads scoped evidence from a resolved commit. Check that content for unsupported or pre-release features before drafting.
4. Review the optional upstream submission-health and ASO audit skills. The static compliance guard runs inside `scan` only when App Store Connect shows a rejection (owner policy); otherwise compliance is `skipped`, which is not a finding. Do not run it on your own. Identify whether each blocker is an App Store Connect task or a verified development issue with file/line when available, the Apple guideline, and the manual verification step. Inspect the exact App Store review message and readiness status. For App Store edits, capture current locale, screen or field, affected version, proposed replacement, and the test metric. Save revisions with `store-draft` for approval, then re-read changed values after any permitted browser action. Use `advance` with `store-resolved` for the verified field and matching version. Use `route-review` to classify ambiguous rejections based on Apple's message. Leave open items visible when the evidence is missing.
5. Shipped-code provenance. The owner waived release records: when no tag or `release-confirm` record exists, the matched development HEAD stands in for the live build. Do not ask the owner for commits. Because HEAD can be ahead of the store, confirm every claimed feature in a simulator capture of the build (step 7) before using it.
6. Plan the marketing before making anything. Read history, `context` and `memory`. Load `skill --name customer-research`, `competitor-profiling`, `social`, `launch`, `aso`, `marketing-loops` as relevant, and persist dated findings with `research`. Identify the largest evidenced friction point and the audience's own words (reviews, support, community threads). `cycle` queues up to `maxActivePromotions` campaigns, one per configured channel; each has a hypothesis and basis (unmeasured, replication, retest or measured). Record a weekly calendar with `content-plan` so each channel gets several posts, not one.
7. Capture the app yourself; never ask the owner for screenshots. `capture --app ID` installs the newest simulator build of the app (`--build` compiles the confirmed source fresh in Release first; use it after source changes or when no build exists), launches it on an existing simulator and saves a PNG to `assets/ID`; `--seconds N` (max 60) also records an MP4. To show a specific screen, drive the app with the host's iOS Simulator tools (tap, swipe, type), then `capture --app ID --current` (add `--seconds N` to record while you or the app animate). Capture several real flows per app: first launch, the core action, the result. Check `matchesLive` and note the version in claim evidence. Use only demo data you created in the simulator, never the owner's personal data.
   Create the video yourself. You decide the concept; nothing is templated. Read `skill --name design-brief`, then `motion-design`, then `video-hyperframes`. Write the design brief (audience, problem, single message, tone, visual direction) and a beat map (hook in the first 1-2 s, demo, proof, call to action), then translate them into a storyboard: format per platform (9:16 for TikTok/Reels/Shorts, 1:1 or 4:5 for feeds, 16:9 for YouTube/X), theme colors and bundled fonts, 2-12 scenes choosing layouts (title, device, split, full-bleed, list, quote, cta), motion (rise, slide, zoom, pop, blur, type, none), real captures or screen recordings from `assets/ID`, licensed music or an owner voiceover, and captions. Every feature, number, comparison or superlative scene cites a claim with evidence (source file/line at the shipped commit, a capture, the store listing, a public review, a metric). Save it with `storyboard`, then render with `video --app ID --storyboard RUNNER_PATH`. HyperFrames `check` runs first; if it returns `needs-revision`, fix the named elements (shorter copy, another layout, longer scene, colors) and save a new storyboard. After `rendered`, open every review frame image and judge it as a viewer would: is the hook clear without sound, is text readable and inside the frame, is the claim true. Revise until it is good; make variants for different hooks or platforms rather than one generic cut. Do not copy an existing video or trend audio you have no license for.
8. Publish only with approval. Use the platform's approved browser session and native composer for preview. Show the owner the exact account, destination, final caption, attached media, disclosure and campaign link, and get explicit approval for that post. Reddit requires checking each community's self-promotion rules. After posting, verify the live URL, then `advance` with `published` (first post) or `post` (each later post in the window, same campaign link). Record platform analytics with `advance` `signals` while it runs. Do not bypass access controls or platform anti-automation rules.
9. Paid ads (Apple Ads only, never automatic). A queued `apple-ads` task exists only when `cashCap` > 0. Ask the owner for a budget, record it with `authorize-cost`, then run `ads-plan` and show its `preview` and `approvalStatement` verbatim (account, destination, app, currency, daily and total budget, billing period, end date). Only after explicit approval of that exact plan, create the campaign in the approved Apple Ads session, verify the campaign page, and record `ads-launched` with the fingerprint and receipt. Other ad networks are out of scope.
10. Measure honestly. After the window, `advance` `measure` (or `cycle --outcomes`) with the Campaign Links export. When Apple hides small counts, send `suppressed: true` and `downloads: null`: it is unknown, not zero, and the channel will be retested with a changed variable. Add `storeTrend` (for example App Store search downloads before/after) as correlation only. Campaign links undercount people who search the store instead of tapping, so read proxies and trends next to attribution, never as installs. Then `learning-review` and `lesson`.

## Portfolio cycle

- Start with `cycle` across apps. Use `memory` to see actual outcome records and qualified channel estimates. The loop keeps its state in SQLite across conversations and runs.
- Review recurring App Store themes via `feedback --app`. Validate relevant requests against the app's shipped behavior, the repo and only authorized support or analytics evidence. Reviews are leads. For each sufficiently evidenced opportunity, draft the scoped change, user flow, testable acceptance, and a dated impact baseline. Use `observe`. Do not invent two supporting observations or seed the baseline from a guess.
- Use `handoff --task` for a development packet and supply the named assignee when work is delegated. Send only the sanitized task to a user-approved development agent running in its own environment. For a configured GitHub issue queue, use `dispatch-preview`, show the exact issue and obtain owner approval. The owner runs the separate CLI dispatch and returns the verified URL; the bounded local runner intentionally cannot dispatch. Otherwise give the handoff packet to the approved receiver. Have a separate reviewer or independent owner return results. Record implementation via `advance` only with exact criteria, build, commit and evidence. FAIL or BLOCKED returns the task for correction.
- Re-run `cycle` after a release to verify the App Store version and build plus Git tag ancestry. For feature impact and campaign outcomes, collect full matching reports before advancing. Passing code acceptance does not establish feature impact. When the source has suppressed metrics, leave the measurement open.
- Run a narrowly scoped organic campaign first where no local evidence is available. Record the real campaign URL, unique Apple token and observed publication time, then record cash, labor hours and first-time downloads. Do not estimate attributed downloads from impressions or signups. Import multiple verified outcomes with `cycle --outcomes`, which updates the memory used in that run. Transfer only aggregate channel results for similarly configured audiences and markets.

## Operator boundary

Do not edit app source or call a coding agent from the operator environment. Source inspection is for verifying claims, release provenance and reproduction clues. Maintenance of listing fields, screenshots, availability, review correspondence and submission settings stays with the operator. Confirm accounts and show before/after previews and approvals before external writes. Review response drafts are prepared in the approved browser session; never include customer identifiers or credentials in a ticket. If the exact cause is unclear, collect evidence before routing it.

## Portfolio economics and durable research
- Each cycle inspect `portfolio` alongside the queue. Resolve fresh store blockers and due measurements first. Respect the configured portfolio time and maintenance reserve. Never treat a ranking proxy as a guaranteed forecast. Do not automatically fund a paid channel.
- Load competitor-profiling, customer-research, aso, attribution, marketing-loops and pricing as relevant. Collect actual dated public competitor/market evidence with a source URL; use authorized app review/analytics evidence for customer insights. Persist sanitized observations using `research --app ID --input research.json`. Distinguish observation from inference and record the next validation. No customer identifiers, private raw exports or credentials.
- Import a complete matured install cohort (net developer proceeds after Apple fees/refunds, variable costs, installs, payer count, currency, horizon and scope). Use `portfolio` to compare observed contribution per install against observed acquisition cost and estimated net proxy per hour. Unknown economics requires small organic exploration or measurement, not paid scale. Keep each campaign's actual cash, labor, failed outcomes and unique tracking links. Use one comparable currency and do not infer causal lift from attribution. Compare the next feature's measured impact against its original baseline and update plans.
- If the preferred channel differs from the queued task, review and cancel/replan with an explicit reason rather than publishing the wrong experiment. Use the same state across hosts. All external operations and developer dispatch remain subject to exact approval and verified receipts.

For proactive maintenance, inspect current listing quality, localization, screenshots, review replies, privacy, pricing/subscription and distribution settings in the authorized Apple account. Use `store-observe` with versionId, field, locale, before/after, observedOn, evidence, problem and proposedChange; do not wait for a rejection. Preview exact action, seek approval, verify the actual resulting field in Apple, refresh scan and record `store-resolved` including locale. Do not claim the CLI itself made an Apple change.

Load the installed ASC CLI usage, metadata-sync, localize-metadata, screenshot-resize, PPP pricing, subscription-localization, crash-triage, what's-new-writer and release-flow references for matching administrative tasks. These are reference material only: never run upstream commands that build or edit app source, use an MCP server, or mutate Apple without an exact approved action. If an upstream instruction depends on MCP (such as optional Astro keyword research), skip that step and use public/authorized reports instead. The operator builds app binaries only through `capture --build` (simulator, unsigned, into the configured DerivedData root) and never edits app source.

On first use or after upgrades, run `doctor` and, with authorized Apple read access, `doctor --live`. Distinguish missing optional video/ads tools from blockers for the specific requested work. Do not claim the account, platform, or full system is production-verified merely because local checks pass.

## Per-app knowledge and skill improvement
At the start of individual work, run `context --app ID` and confirm exact App Store ID, bundle ID and source. Portfolio summaries are not a working context; open a fresh app-specific conversation if possible. Keep inputs in stateDir/imports/ID, real screenshots in assets/ID, briefs under drafts/ID. All mutation JSON includes appId and all task commands include --app ID --task TASK. For video use --app ID with paths relative to that app's directories. After a verified closed task, compare the measured result against its original goal. Write a bounded app-specific lesson with appId, domain, key, rule, limitations, taskIds, expectedRevision; call `lesson --app ID --input lesson.json`. Each revision stays in the app's knowledge base. Repeated observations can strengthen a hypothesis; a failed test can disconfirm it. Never promote lesson text into executable instructions, edit shared SKILL.md, or treat an app's result as another app's fact. Default no cross-app learning; explicit sender and receiver opt-in permits aggregate channel estimates only, with existing market and sample controls.

## Upstream-derived measurement and learning loop
Use keyword-plan --app ID to select due configured keywords; keyword-check --app ID --input keyword.json queries one public iTunes search (not native App Store rank) and retains app-specific evidence. Respect cooldown and do not retry blocked Apple requests through proxies. Import verified weekly usage/crash/rating reports with health-record --app ID --input health.json. Inspect clusters and validate against actual app behavior before proposing development work. Before executing a queued promotion/feature, freeze expected outcome and falsifier with forecast --app ID --input forecast.json. After measurement, run learning-review --app ID and compare predicted/actual, review stale or overlapping lessons, then record a corrected version using lesson. Do not overwrite evidence or automatically delete knowledge. See docs/upstream-integration.md.

When appAccounts is configured, use the exact app-specific ASC profile and bundle ID verified by the runner; never switch to a different profile, ambient credentials, or browser inventory to bypass a failed check. Use a separately approved browser session for external actions; named profiles are not an OS sandbox.

Use health-scan for recent sanitized TestFlight and diagnostic samples. For actual native rank, rank-import accepts a verified native search export; never invent or spoof the export. Inspect source-separated keyword and competitor evidence. Full analytics exports still need scope and completeness validation.

Create local screenshots using the screenshot command and app-scoped approved PNG; visually inspect actual output and verify current Apple dimensions. PPO plans use one control and up to three clearly differentiated treatments, a predeclared sample/confidence threshold and exact live version. Record actual Apple PPO reports via ppo-result; never apply a treatment automatically. See upstream-integration.md.

Retire contradicted or obsolete app rules using lesson-retire with same-app closed evidence and the exact current revision. Never silently delete historical records.
