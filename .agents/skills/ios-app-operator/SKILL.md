# iOS app operations

1. Confirm the selected Apple developer team and the requested apps. Run `npm run agent -- apps`, then `scan` for one App Store ID or all configured apps. Show the two reporting windows, data source and gaps. Sales units, developer proceeds, payments and ad spend are separate measures. Currency and channel scope stay attached to each figure. Unknown and privacy-suppressed are not zero.
2. If the API is unavailable, ask the user to open their authorized browser profile and log in manually. Use Chrome DevTools MCP or the host's supported computer-use tool. For account UI, only open the applicable dashboard returned by `browser --platform asc` or `ads`. Confirm the team and app. Read Apps, version/build state, Sales and Trends, App Analytics and Apple Ads totals as authorized. Put observed numbers and explicit periods in the operator metrics schema and rerun scan. Describe fields left out and why. Do not retain cookies, login details, private screenshots or secret values in the metrics file.
3. Resolve the source using the precise bundle ID, repo/folder, Git commit, App Store live version, review candidate, and newest uploaded build. Ask when distinct sources remain plausible. A matching tag is evidence of version naming and needs a release record or user confirmation before claiming it built the deployed binary. `inspect` reads scoped evidence from a resolved commit. Check that content for unsupported or pre-release features before drafting.
4. Review the optional upstream submission-health and ASO audit skills. Run the configured static guard against the exact source. Turn each suspected blocker into an evidence-backed issue with file/line when available, the Apple guideline, and the manual verification step. Inspect the exact App Store review message and readiness status. For App Store edits, capture current locale, screen or field, affected version, proposed replacement, and the test metric. Save revisions with `store-draft` for approval, then re-read changed values after any permitted browser action.
5. Read history before proposing a promotion. Identify the largest evidenced friction point and choose one intervention with a prediction and a way to measure it. Use the installed Marketing Skills social, analytics, and launch workflows. Use OpenDesign design-brief and motion-design for the audience, beat map and visual continuity. OpenDesign video-hyperframes can supply a storyboard structure. Produce a draft with `brief` and a vertical MP4 with `video`; allow a richer editable composition through HyperFrames or Remotion only when appropriate and licensed. Use verified app captures, licensed assets, truthful claims, and captions when useful. Avoid copying an existing video or running bundled third-party telemetry commands.
6. Use the chosen platform's approved browser session and native composer for preview. Confirm account and audience settings, final text, attached media, disclosure, and destination. Follow the project approval rule before submitting or scheduling anything. Reddit requires checking each individual community's self-promotion rules. Do not bypass access controls or platform anti-automation rules.
7. Save the final experiment via `record` with its hypothesis, platform, version, commit, campaign token, and observed URL or outcome. Recheck performance after the platform and Apple have reported enough data. Apple campaign links and platform analytics can show attributed outcomes, not guaranteed incremental lift. Use comparable time periods and record confounders.

## Portfolio cycle

- Start with `cycle` across apps. Use `memory` to see actual outcome records and qualified channel estimates. The loop keeps its state in SQLite across conversations and runs.
- Review recurring App Store themes via `feedback --app`. Validate relevant requests against the app's shipped behavior, the repo and only authorized support or analytics evidence. Reviews are leads. For each sufficiently evidenced opportunity, draft the scoped change, user flow, testable acceptance, and a dated impact baseline. Use `observe`. Do not invent two supporting observations or seed the baseline from a guess.
- Use `handoff --task` for a development packet and supply the named assignee when work is delegated. Send only that app's packet to a user-approved development agent, such as `ios-feature-builder`, with its isolated checkout. Have `ios-acceptance-reviewer` or an independent owner return results. Record implementation via `advance` only with exact criteria, build, commit and evidence. FAIL or BLOCKED returns the task for correction.
- Re-run `cycle` after a release to verify the App Store version and build plus Git tag ancestry. For feature impact and campaign outcomes, collect full matching reports before advancing. Passing code acceptance does not establish feature impact. When the source has suppressed metrics, leave the measurement open.
- Run a narrowly scoped organic campaign first where no local evidence is available. Record the real campaign URL, unique Apple token and observed publication time, then record cash, labor hours and first-time downloads. Do not estimate attributed downloads from impressions or signups. Import multiple verified outcomes with `cycle --outcomes`, which updates the memory used in that run. Transfer only aggregate channel results for similarly configured audiences and markets.
